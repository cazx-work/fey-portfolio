# Portfolio Priority Ranking

## Tier 1 (Must Show)

### 1. AES70 SDK and protocol abstraction
**Why:** The clearest evidence of protocol engineering, typed API design, serialization, asynchronous command handling, and architectural ownership. Recruiters see specialized impact; hiring managers see abstraction quality; senior engineers can discuss boundaries and tradeoffs.

### 2. Configuration recall and conflict resolution
**Why:** Demonstrates recovery-oriented state design, identity matching, validation, compatibility, and safe restoration in a changing hardware topology. This is more distinctive than ordinary persistence.

### 3. Grid layout engine plus matrix conversion
**Why:** Together they show domain modeling, non-uniform layouts, graph/matrix transformation, validation, deterministic updates, stereo/split semantics, and protocol-safe mutation.

### 4. Device lifecycle and state retention
**Why:** Demonstrates ownership of unreliable external systems, reconnect behavior, resource cleanup, stream coordination, and durable user intent.

### 5. Layered testing and BDD integration platform
**Why:** Shows that the system was designed to be changed safely. The reusable test platform is particularly strong evidence of leverage and developer experience.

### 6. Rive performance and interaction boundaries
**Why:** Include as evidence of performance engineering when supported by profiling or frame/rebuild comparisons. It shows practical optimization under a real workload.

## Tier 2 (Important)

### 7. Repository ownership architecture
**Why:** This is foundational and should be merged with state retention rather than shown as a separate feature. It demonstrates state ownership, online/offline parity, and decoupling.

### 8. Module ganging system
**Why:** Strong domain and event-propagation story: absolute versus relative semantics, delta calculations, origin tracking, and multi-host membership. Feature it as a focused case study inside the signal-path section.

### 9. Linux test environment automation
**Why:** Valuable developer-enablement story showing process ownership, reproducible environments, hardware substitution, and thoughtful use of Copilot. Keep concise and clearly state review and validation responsibility.

### 10. Structured KeyService
**Why:** Good supporting evidence for testability and UI contracts, but less impressive as a standalone headline. Merge into the testing/Developer Experience section.

## Tier 3 (Optional)

### 11. Detailed dashboard architecture modernization
**Why:** Useful evidence of maintainability and refactoring judgment, but generic feature layering is less distinctive than protocol, lifecycle, and routing work. Summarize as the architectural foundation for the performance story.

### 12. Detailed test evidence maps and file inventories
**Why:** Helpful for senior engineers validating claims, but distracting in the main narrative. Put behind `Read more`.

### 13. Full edge-case inventories
**Why:** Preserve representative examples—stereo, split, missing devices, reconnect, feedback loops—but hide exhaustive lists.

## Tier 4 (Remove from the primary experience)

### 14. Repeated portfolio cards and repeated senior-engineering bullet lists
**Why:** They duplicate the same message and make the portfolio feel generated rather than curated.

### 15. Generic Flutter/Dart skill lists
**Why:** Technologies alone do not establish impact. Mention them in metadata, not as content.

### 16. Unmeasured performance claims
**Why:** Claims such as “smooth” or “reduced jank” should be removed or qualified unless supported by profiling, frame timing, or a clear before/after observation.

### 17. Exhaustive class names, folder paths, and implementation mechanics
**Why:** They are evidence, not the story. Keep a small number of links or expandable citations for technical reviewers.

## Recommended featured sequence

1. Product context and engineering scope.
2. Architecture ownership: repositories, lifecycle, and protocol SDK.
3. Signature domain story: Grid → matrix conversion → configuration recall.
4. Quality platform: layered testing, BDD, semantic keys, and Linux test doubles.
5. Performance under real interaction load.
6. Tradeoffs and future improvements.
